# xmip-core-transport-azure-blob

Azure Blob transport: Shared Key over the Blob REST API — list a prefix, get each blob and delete it once the runtime accepts it, put a Stream as a block blob — a container prefix is a Location. A technology of [xmip-core-transport](https://github.com/IlleNilsson/xmip-core-transport).

Shared Key comes from [xmip-core-transport-azure](https://github.com/IlleNilsson/xmip-core-transport-azure), where every Azure technology shares what Azure speaks over HTTP (ADR-0044, amendment 2026-09-24); HTTP itself comes from [xmip-core-transport-http](https://github.com/IlleNilsson/xmip-core-transport-http).

Requests go on connections kept between them (`http::endpoint::Connections`, offering HTTP/1.1): the transport holds them and hands them to every client it makes, so a call costs one exchange and not a connect, a TLS handshake and a `Connection: close`, as it did until 2026-09-27.

A Location signs as the storage account its `account` setting names, with the account key its `secret = "<name>"` names: a `password` secret holding the key in base64, as the portal shows it, kept in the Administration Database and never in configuration, read at each request, a send and a receive's listing, get, claim and delete alike, so a key set again reaches the next request without a restart (ADR-0019, amendment 2026-10-29; ADR-0015, amendment 2026-11-25).

## One node receives a blob

Several nodes may list one container; each blob is received by one of them (ADR-0024, amendment 2026-11-20). A receive claims each blob it hands over by a Put Blob of `<name>.xmip-claim` beside it with `If-None-Match: *` (`Client::put_new`), which the service performs "only if the resource doesn't exist, and fail[s] the operation if it does exist" ([conditional headers](https://learn.microsoft.com/en-us/rest/api/storageservices/specifying-conditional-headers-for-blob-service-operations)). The claim holds the claimed name the file family records, the blob's name, the node's location, which start of it claimed and the time in nanoseconds; a blob whose claim is listed is passed over without a request, and one whose put the service refuses is passed over. The sequence is the capability's, written once (`transport::listed::Claims`); this crate implements only the container's calls (`container::Container`, `transport::listed::Store`). The claim is deleted with `If-Match` its own `ETag` however the cycle ends — after the blob on Accepted, alone on Refused and Failed — and one the service does not answer is deleted at the next listing. A node that starts again (`Configured::on_node`) reads each claim listed at its first receive that reaches the service and deletes every one an earlier start of the node holds, never one of its own start, whichever of its Locations made it, so a Location built while another of the same start receives over the same prefix leaves what that one holds (ADR-0024, amendment 2026-11-22); another node's claim is left whatever its age, so a node gone for good leaves its blobs claimed and in place. Not a blob lease: [Lease Blob](https://learn.microsoft.com/en-us/rest/api/storageservices/lease-blob) "creates and manages a lock on a blob for write and delete operations", so a producer could not write the blob again while Xmip held it, and a lease lasts 15 to 60 seconds or forever, to be renewed through a long cycle or broken after a death. Per object the claim costs one conditional Put Blob at the listing and one Delete Blob at its verdict, and the Location's credentials need write for it. `Transport::claims` answers the same claim for one blob by its address.

## How a received blob is acknowledged

A receive deletes nothing and gets nothing: it lists the prefix, and each blob's `GET` is made when the runtime first reads its body (`transport::listed::Claims::listed`, the capability's one object-store receive, over `transport::body::fetched`), whole (`net::http` reads a response body whole), so a receive that lists a hundred blobs holds none of them in memory. Every blob stays in the container until the runtime gives its verdict after the whole receive cycle (runtime-model section 5). Accepted deletes the blob. Refused leaves it where it lies — a refusal is not a consumption, and a Stream refused at a transport gate was never written to the Ledger, so the blob is the only copy — and this Location does not receive it again while its `Etag` is unchanged (`transport::Refused`, which the listing is sifted through: the client lists each blob with the `Etag` in its `Properties`, read by the capability's one listing scan, `transport::listed::Listing`); one written again under its name has another `Etag` and is a new arrival. The memory is the node process's: a node started again receives a refused blob once more, refuses it once more, and remembers it from then on. Failed leaves it, and the next receive lists and gets it again. Until 2026-10-02 a receive got every blob it listed before handing any on. No lease is taken, so none is released. A crash before the verdict leaves the blob too, claimed until its node starts again: at-least-once, never a loss. The delete is the one the receive made until 2026-10-02, so a verdict adds no request but its claim's delete.

The get and the delete hold to the blob as it was listed (ADR-0024, amendment 2026-11-19): each carries `If-Match` with the `Etag` the listing gave, quoted. A blob written again between the listing and the first read answers the get 412 `ConditionNotMet`, or 404 `BlobNotFound` where it was deleted, and is not read under the old `Etag`: the read fails, the cycle fails, nothing is deleted, and the next listing takes it as a new arrival. A blob written again between the read and the acceptance answers the delete the same way and stays for the next listing, and the acceptance is told done. Any other 412 or 404, a lease's or a container's, is the failure it is. The condition rides on the calls the receive made already, so it adds no request. Until 2026-11-19 both were unconditional, and a replacement written between the read and the acceptance was deleted unread.

A receive's claim and an archive write with `Client::put_new`: Put Blob with `If-None-Match: *`, which never writes over a blob already there, and hands back the `ETag` it stored. The conditional-header tables answer it 412 where one is there, the service 409 `BlobAlreadyExists`; both say "there", and the blob is left as it was. A send still puts over what lies at its target. Microsoft's sources: [conditional headers](https://learn.microsoft.com/en-us/rest/api/storageservices/specifying-conditional-headers-for-blob-service-operations), [Get Blob](https://learn.microsoft.com/en-us/rest/api/storageservices/get-blob), [Delete Blob](https://learn.microsoft.com/en-us/rest/api/storageservices/delete-blob), [Put Blob](https://learn.microsoft.com/en-us/rest/api/storageservices/put-blob), [error codes](https://learn.microsoft.com/en-us/rest/api/storageservices/blob-service-error-codes). Shared Key signs `If-Match` and `If-None-Match` among its standard headers. The session, the far end a test binds, holds every request to the condition it carries as the service does.

A send target is read by `net::Target` in [xmip-core-library-net](https://github.com/IlleNilsson/xmip-core-library-net), the one reading of a URI every technology calls: scheme, authority, path and decoded query. Until 2026-09-28 it was read through the transport capability's `socket::target`, which split it on its first slash and left the query in the path.
